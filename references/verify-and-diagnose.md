# 验收和故障处理

verified_against: v26.9.30；固定默认 A′；真实链路记录见 docs/test-records。
执行者先定位症状，不先轮换密钥或重新安装。
旧版 check-live-auth 的 PASS 存在误报风险，基于它的验收须按新版复验；
修复与测试边界见 [验收修正记录](../docs/test-records/2026-10-07-validation-fixes.md)。

## 从状态到实际连接

```sh
scripts/check-service.sh --json
```

该辅助脚本只输出结构化检查结果，临时启动同版本客户端，结束清理客户端并保留服务。
它覆盖服务 active/enabled/运行时限、专用用户、配置/无中继限速、回环端口、公共证书链/域名/有效期/密钥匹配、Certbot
定时器/部署钩子/续签演练证据、A/B 同 core 代理和认证反例、CF 根路径、非 CF 伪造 CDN SNI。
公共证书或续签设施未验证时标 FAIL。缺少演练证据时按 [证书规程](certificates.md)
运行 `scripts/check-certbot-renewal.sh --dry-run`，普通 dry-run 不运行 deploy hooks，不能代替它。
不把它称为原始计划 V01–V21 的全覆盖程序。

执行者还要补充：

1. **外部入口**：有可用外部测试环境时确认 VPS:443 可达；以正确伪装 SNI 访问得到真站证书/响应，
   随机 SNI 在默认策略下失败。端口开但代理不通时继续看认证，不只测 ping。
   没有外部测试机时继续本机部署和检查，将外部入口标为未测试，不把另一台 VPS 当作本机部署前提。
2. **出口**：临时客户端 curl CF trace，脚本内部比较出口 IP 与 VPS 可用 v4/v6，
   只回传相等/不相等，不显示地址/节点。
3. **B TLS**：确认生成和导出的 B JSON 无 `echConfigList`、新 URI 无 `ech` 参数，SNI 为 CDN 域名。
   对国内 B 不通/A 正常的旧客户端，先按 [客户端规程](client-compat.md#已有-b-客户端移除-ech) 移除 ECH，
   不同时调整 ML-KEM、packet-up 或服务端。目标机自测不能替代用户所在国内网络的最终实测。
4. **目标**：重新执行 check-reality-dest.sh；目标协商 X25519 是允许行为，不误报后量子握手成功。
5. **客户端**：收集软件/内置 core 版本，按 client-compat.md 核对；不要要求用户贴真实 URI。
6. **变更后**：对比私有 links.txt 是否变化，只输出比较结果。服务留运行，临时客户端全部退出。

## 典型问题

| 症状/检查结果 | 优先处理 |
|---|---|
| A/B 都不通，S01 失败 | 服务是否被停止、未自启或设 RuntimeMaxSec；核对 -test 后恢复常驻服务 |
| 443 被其他进程占用 | 识别既有服务，不杀未知进程；按授权备份/迁移 |
| A 失败，B 正常 | 目标状态、时钟、core/指纹是否提供混合群、shortId/ML-DSA 是否被客户端丢弃 |
| B 失败，A 正常 | 检查旧客户端残留 ECH；再查 CF 橙云/回源 SNI、WAF/缓存、TLS 证书/模式及 Encryption/packet-up，逐项验证 |
| CF 521/522 | 服务或端口不通、安全组、错误源站地址 |
| CF 525 | CF 到源站 TLS 握手失败；核对监听、SNI、协议、证书和链 |
| CF 526 | CF 拒绝源站证书；核对实际生效的 Full (Strict)、SAN、信任链及有效期，见下文 |
| CDN 根路径 404 | 仅旧部署/website off 正常；网站模式应为 200 且正文匹配当前页面 |
| 直连伪造 CDN SNI 成功 | 检查 CF 来源规则、PROXY v2 链，不扩大信任范围来“修复” |
| CLI JSON 成功，GUI 失败 | 导入字段/客户端 core 支持问题，让用户用私有 JSON 验证 |
| 导出成功但节点不可用 | 导出不启动服务；先回到 S01/实际代理检查 |

## 私密诊断方法

不要 cat config、journalctl 全文、原始错误日志或抓包返回给模型。
在目标机写有限的检查程序：固定错误类别返回 ID/布尔值/计数，禁止输出错误上下文中的密钥。
如确需检查新错误形态，先用合成配置复现并测试脱敏，再对实际文件执行同一检查。
所有临时配置与客户端日志放 700 目录，文件 600。旧模式 8002 接收 PROXY v2；网站模式则是
8003 的 Nginx 接收 PROXY，8002 的 Xray 不接收 PROXY。检查实际配置后再选探针，
不能用不匹配的裸 openssl 失败来断言源站证书坏了。

## 基线结果与 526

check-live-auth 必须检查 curl 退出码和 trace 格式；非零退出、空/错误响应不能打印 PASS。
A、B 基线分别报告；任一失败跳过鉴权反例，总验收失败。反例之后再跑正例，避免把断网或
源站故障误当作鉴权生效。HTTP 526 不是“错误凭据被拒绝”的有效证据。

526 表示 Cloudflare 认为源站证书无效，通常对应 Full (Strict)。在网站模式下，CF 首先看到
Nginx 8003 的证书；Nginx 到 Xray 8002 的 TLS 验证失败通常呈现 502，是不同的一段链路。
按以下顺序检查，输出布尔值/固定错误类别，不打印证书、私钥、配置或原始日志：

1. 实际 SSL/TLS 模式及域名级 Configuration Rules/Origin Rules 是否覆盖 zone 配置；
   无 CF API 权限时让用户确认面板状态，不声称已经读到了设置。
2. 橙云记录的源站地址、回源 SNI 是否正确；实际服务呈现的证书是否覆盖 CDN 域名、未过期、链完整。
3. 若为旧版 Skill 自签证书，按 [证书规程](certificates.md) 迁移到 Let’s Encrypt 公共证书，
   接入 Certbot 自动续签和部署钩子。不得通过降低 CF 校验来解决 526。
   不自动降级校验、不改灰云、不打开 allowInsecure，也不把 REALITY 伪装站换掉来处理 526。
4. CF Origin CA 与公共 CA 不是同一种信任来源，本版要求公共 CA；Origin CA 不满足要求，
   同样迁移到公共证书。不能给系统随意添加私有信任根来绕过检查。
5. 修复后重测 CF 首页、真实 B 基线和鉴权反例；本地隔离测试通过只能说明拓扑可行，不能覆盖实际 526。

## 普通用户的隔离测试

local-website 测试不要求 root，Nginx 优先从 PATH 查找，再检查 `/usr/sbin/nginx`。
P01 表示没有找到可执行 Nginx，P02 是端口参数不合法，P03 是指定 Xray 不可执行。
先处理具体前置条件；本机 sudo 能执行不能说明节点本身原先有问题，也不意味着要连接远程 VPS。
若测试 core 位于 root 私有目录，用已授权的 sudo 运行测试或复制已验证的二进制/公共 geo 资产
到调用用户可读的测试目录；不要放宽真实配置和密钥的权限。

验收报告分别列已测、失败和未测；不能因同版本测试客户端通过就声称用户 GUI 已通过。
