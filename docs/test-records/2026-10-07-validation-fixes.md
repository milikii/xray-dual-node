# 实测反馈后的验收修正

用户反馈：本机通过普通用户和 sudo 维护节点，旧验收可能在 B 基线失败时输出 PASS；
实际 B 请求遇到 Cloudflare 526，普通用户运行网站集成测试在前置条件处失败。

## 已确认与修复

- check-live-auth 的成功分支使用 `[[ status == 0 ]] && grep ...`，首个条件失败并不会可靠地
  触发 Bash errexit，后面的 PASS 仍可执行。改为显式结果判定、非零返回和独立 A/B 结果。
- 函数在条件上下文调用时不依赖 errexit；渲染、配置检查、进程启动/就绪失败均直接失败。
- 基线失败不继续反例；反例中的 526 不算有效鉴权拒绝，结束时重测正例。
- check-service 单独返回 A、B 的基线结果和 525/526 分类，实际 Cloudflare 失败不能被本地测试覆盖。
- local-website 在 PATH 没有 nginx 时检查 `/usr/sbin/nginx`，前置条件分别返回 P01/P02/P03。
  原第 29 行同时检查 Nginx 和端口，仅凭行号无法确定现场唯一原因。

## 验证

- 七项真实 Shell 验收入口回归测试，命令依赖使用合成替身：A/B 失败、无有效 trace、配置错误、
  错误凭据意外成功、反例阶段 526、完整预期结果；失败不报 PASS，测试秘密不出现在输出中。
- 以 nobody 用户、`PATH=/usr/bin:/bin` 运行完整隔离网站集成测试，使用临时复制的已验证 core 和代码。
  通过静态站、原子更新、A/B 多 MB 上传下载、错误凭据、来源/SNI 反例、后端错误及实际准备入口。
  没有修改系统服务或用户节点，没有为测试放宽实际节点文件权限。
- Skill 校验、Shell 语法/lint 和 diff 检查通过。

## 证据边界

本次没有访问用户截图中的运行环境，未修复或宣称其 526 已消失。
旧记录中仅凭 check-live-auth 的 PASS 不能证明基线成功，需要使用修正后的脚本现场复验。
此前独立 Python 集成测试的断言不依赖该 Shell 判定，保留其本地验证范围。
